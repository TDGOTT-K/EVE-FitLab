# FitLab 计算引擎全面审查与重写决策

日期：2026-09-14。审查基线：`860b8d782e1d4022c80fd87fb87dae25056b14a7`。

## 决策

**当前引擎不能作为普遍可信的配装数值权威；但不建议把整个计算系统从零完全重写。建议保留已验证的基础能力，分层替换效果执行核心及事件模拟，消除 Python/C# 重复计算。**

这不是只修四个 DPS 技能就能解决的问题。已确认的错误覆盖伤害、推进、维修、电子战、远程作用距离、电容以及 API 汇总。另一方面，基础 HP/CPU/栅格、若干通用技能、普通炮塔与脚本、采矿晶体、基本回充和命中公式都存在明确正确样本。全盘推倒会丢掉这些可复用能力，同时仍然要重新补全相同的 EVE 特殊机制。

建议的技术方向：继续以 C# 承载唯一的数值核心；Python 保留 API、存储、角色快照及调用编排，不再修补 C# 属性或另建一套相同指标的数值语义。语言并非正确性的决定因素，**规则覆盖、唯一权威、可验证契约和独立基准才是**。

本轮只修改审查文档和本地探针，未修改生产计算代码，未发布新版本。

## 审查方法和证据强度

覆盖完整桌面运行链路：

```text
前端装配/技能/靶标
  → server.py：导入文本、状态及技能快照
  → C# InMemoryFitService → DogmaFitAdapter
  → SDE/规则加载 → FittingCalculator → 元数据与聚合属性
  → server.py 再修改维修属性
  → capacitor.py / sustained_tank.py / linked_scenario.py / fitting_scenario.py
  → calculation_graph.py
  → engine-view.js / defense-profile.js / extended-stats.js / 分享图
```

- 当前原有 Python 测试：**42 项通过**；前端防御数学与无人机拆组测试通过。
- 新增本地审查：**37 个真实 SDE 装配场景**，包含无技能/全 V、普通与超规格推进、炮塔状态/脚本、维修与远程维修、辅助维修、电子战、注电、堡垒、采矿晶体。
- 独立公式/契约检查：**83 项，60 项符合，23 项不符合**。其中同一缺陷在多艘船上重复出现；23 不等于 23 个独立根因，也不能据此推断“整体正确率”。
- 前轮用户图精确快照的 8 个技能差分场景继续作为证据，详见 `dps-audit-2026-09-14.md`。
- Pyfa 参考固定在 commit `8b04f3b271e614b3e103853b44a7851a63d79d0e`。炮塔期望、导弹应用使用其纯数学函数对照；推进、技能及部分特殊效果使用对应处理器核对规则。**未启动完整 Pyfa 数据库计算全部装配，也未取得游戏客户端实测对照。**
- 使用本项目的 SDE **3248221 / 2026-03-10** 做数值输入，不能把结果当作对当前服务器所有平衡更新的认证。打包规则文件头声明 build 3307202，与 SDE 不同，当前流程没有兼容性验收；这属于来源控制风险，不能仅凭版本不同断言某项数值错误。

审查覆盖了运行架构和主要数值领域；没有穷举数千装备的所有组合。已确定错误、已通过样本和待核准机制在下文分开说明。

### F01：规则不完整，不是技能快照没有传进去

`FittingCalculator.cs:1749` 对没有 `modifierInfo` 的效果直接跳过。轻型导弹伤害效果 660/661/662/668、导弹专精 1851、无人机技能 1730 没有补充实现。四项技能分别从 V 改成 0，输出完全不变。

Pyfa 对这些效果有明确的按来源技能筛选目标的处理器。仅让 JSON 含有一个“看起来正确”的加成还不够，必须避免不同弹种、族别或 T1/T2 装备之间串加成。

对目录内装备关联效果做交叉清单，找到 **79 个“官方条目缺通用 modifierInfo、Pyfa 有具体处理器”的候选效果**。其中普通射击、维修、推进有些已被 FitLab 手工计算，**79 不是已确认遗漏数量**。这个清单说明必须建立效果覆盖清单，不能再把“字段存在/轨迹完整”当成规则齐全。

### F02：推进公式中的无依据封顶

位置：`FittingCalculator.cs:2320`。

```text
当前：质量系数 = clamp(推力 / 总质量, 0, 1)
应为：推进后速度 = 基础速度 × (1 + 速度加成 × 推力 / 总质量)
```

全 V 裂谷级 + 10MN 加力燃烧器 II + 微型辅助能源核心 II，经引擎判断装配合法：

```text
456.25 × (1 + 1.6875 × 15,000,000 / (1,067,000 + 5,000,000))
= 2,359.7984 m/s
```

当前封顶后只有 1,226.172。不能通过普通尺寸推进模块通过测试来证明此公式正确。

### F03：远程修甲被扣了两次

位置：`DogmaFitAdapter.cs:1000`、`server.py:132`。

C# 已将组 325 远程修甲从本地维修排除；Python 又从本地修甲减去远程输出。中型修甲器 II 本地 40.888889，加上远程修甲 II 的 42.666667 后被减成负数，再 `max(0, ...)` 掩盖成 0。

远程护盾组不在 C# 相同分类清单内，所以 Python 扣除在护盾样本里反而正确。这是跨层补丁对不同模块类别产生不同语义的直接证据，不能只删掉一行而不先统一分类契约。

### F04：辅助维修不是普通“属性 / 周期”模块

位置：`FittingCalculator.cs:333` 起的维修投射、`:498` 的耗电投射；特殊效果 4936/5275。

- 中型辅助护盾回充器 + 海军注电 50：装弹阶段应消耗弹药而不消耗舰船电容；当前仍按 198 GJ / 3 s = 66 GJ/s 计算。
- 中型辅助装甲维修器 + 纳米体修复粘合剂：应应用 `chargedArmorDamageMultiplier = 3`；当前输出 207 / 9 = 23，而不是 621 / 9 = 69 HP/s。
- C# 已输出 32 单位弹夹及每轮消耗 4 单位，实际是 8 轮。Python 后续也没有完整消费这些契约字段。

这同时污染理论维修量、电容稳定性和持续维修量。

### F05：炮塔 falloff 不等于远程效果 falloff

位置：`FittingCalculator.cs:266`、`linked_scenario.py:34` 起。

投射统一读取 `falloff`，未读取远程效果使用的 `falloffEffectiveness`。数据缺失又落到默认 1，Python 无法区分真实射程与默认值。

中型能量中和器 II：最佳 10 km，失准 5 km，15 km 处应是 180 × 0.5 = 90 GJ/轮；实际传给 Python 的失准为 1 m，输出约 `8.9e-322`，实质为 0。中型远程修甲 II 同样含 3,000 m 的 `falloffEffectiveness`，却输出 1 m。

### F06：导弹公式正确，输入量定义错误

位置：`app.js:422`、`linked_scenario.py:25`、`fitting_scenario.py:49`。

前端设置的是双方相对速度，上限是双方最大速度之和；同一个 `speed` 被直接传入导弹伤害函数。导弹速度减伤需要目标自身速度，炮塔跟踪才需要双方相对运动形成的角速度。

例：目标信号半径 125 m、爆炸半径 100 m、爆炸速度 100 m/s、指数 0.6。目标静止，攻击者以 2,000 m/s 运动时，当前输入得到 `0.0625^0.6 = 0.18946`；目标自身速度为 0 时应为 1。仅有一个相对速度向量无法反推出两艘船的绝对速度，需要修改输入模型。

### F07：Python 使用了不同于 C# 的叠加惩罚

位置：`fitting_scenario.py:72`。

当前 `exp(-(i / 2.22292081)^2)`；参考公式为 `exp(-i² / 7.1289)`，第二项应约 0.86912。C# 使用的 0.8691199808003974 幂序列与参考吻合，Python 另写公式时引入错误。

### F08—F10：Python 事件模拟和换弹契约需要统一

位置：`sustained_tank.py:15–16`、`:26–34`、`capacitor.py:58–63`、`fitting_scenario.py:42`。

- 持续维修仅对注电器组 76 处理弹夹及换弹，辅助维修器持续按满速重复。为隔离 C# 耗电错误，将 ASB 耗电修正为 0 后再测：当前 48.6667；按 9 轮 × 3 s + 60 s 换弹，在同一 1,200–1,800 s 采样区间是 15.33 HP/s。它不是“采样误差”。
- `capacitor.py` 将同刻本舰耗电合计后先扣除，再算外来收入；`sustained_tank.py` 按堆排序，负索引外部事件先执行。按项目自己的先付出规则，100 GJ 容量、每秒耗 100 GJ 回盾 100 HP、外来每秒传 100 GJ，应隔轮成功，持续 50 HP/s；当前维修模拟每轮成功，报告 100。
- `magazineCapacity` 是弹药单位，`chargeUnitsPerCycle` 是每次消耗；Python 换弹没有除后者。32 单位、每轮 4、周期 9 秒、换弹 60 秒的合成武器，正确占空比为 72/132；当前用 288/348。这是契约层构造反例，不冒充截图武器也每轮消耗 4 单位。

### F11—F13：同名汇总字段存在多个真值

- 换弹：`FittingCalculator.cs:1081` 对导弹短路返回纸面 DPS，`:3194` 又把低于理论 80% 的结果强行抬回；UI 通过 Python 另算，恰好遮住底层错误。
- 分层 EHP：`DogmaFitAdapter.cs:1316` 取四种单伤 EHP 的算术平均，即 `mean(HP/resonance)`；均匀混合来伤应为 `HP/mean(resonance)`。总 EHP 来自另一条正确的路径，前端防御视图又自行按权重重算。因此 API 分层 EHP 相加不等于总 EHP。该错误不等于当前界面所有 EHP 都错误。
- 峰值电容：`DogmaFitAdapter.cs:1015` 通过 `UsePerSecond + PeakDelta` 推导峰值，而 `FittingCalculator.cs:3147` 在无耗电时未填正确 delta。裸船返回 0。Python `2.5*C/T` 正确，UI 取 Python 时看不出底层错误。

## 架构风险：不能把它们都包装成已复现数值错误

以下是代码审查确认的结构风险，尚未为每项构造游戏装备数值反例：

1. **效果不是一个完整的对象依赖图。** `CollectEffectsForTarget` 对非 ItemModifier 的部分函数没有完整限定 domain；无人机 `itemID` 判断只比较种类，不区分具体对象；目标状态采用数值等级比较（`:3008`），Target 比 Active/Overload 更大。继续扩充规则前必须定义 ship/character/module/charge/drone/target 的作用域与状态语义。
2. **循环依赖返回基础值。** `GetEffectiveTypeAttributeValueById:1577` 遇到递归直接返回 base，没有向上报告不完整；可能让未来补充效果的循环看起来成功求值。
3. **正值回退和 Math.Max 掩盖不一致。** 部分缺失值、合法 0、默认值和错误值不能区分。最终 DPS 还会在两个聚合来源中取较大值，没有证明某一来源是权威。
4. **轨迹完整度只有局部意义。** `calculation_graph.py` 能检查记录的算术是否复现，但被跳过的效果从未进入图，所以无法证明“没有漏算”。需要独立的 effect coverage/computation validity。
5. **运行链路与备用实现并存。** 普通桌面装配走 DogmaAdapter；`Internal/FitComputationEngine` 是缺 Dogma 类型时的近似备用路径，采用加法型快照汇总/平均耗电等方式。它不是本轮 37 样本的数值来源，应隔离、标明近似或移除，不能当成第二个权威。`stats.js` 的早期基础计算也不是当前 `renderShipStats` 的主路径。

## 明确尚未核准的边界

- 所有舰船、所有 T3 子系统、植入体/增效剂/环境效果的完整组合；桌面输入没有把所有 C# 支持对象都暴露出来。
- 电容战真实目标是否有足够电容、吸电百分比条件、友方来源缺电后的停机；当前项目已有假设声明，不能把假设成立时的模拟冒充完整联算。
- 无人机追击与往返、导弹加速与边界射程、目标几何半径、完整热损伤、反应式抗性及复杂预热/重激活时序。
- ECM 类型匹配、投射抗性、电子战对目标属性与本舰伤害的闭环联算；当前更多是输出展示，未达到完整战斗模型。
- 辅助模块弹药耗尽后选择停机、换弹还是无弹运行，需要明确产品策略。

对这些边界应给出“未模拟/条件假设/缺失规则”的明确状态，不能输出一个没有条件说明的可信数值。

## 重写方案比较

| 方案 | 判断 | 原因 |
| --- | --- | --- |
| 只补四项 DPS 技能后继续开发 | 不够 | 已有多个独立领域出现严重错误 |
| 在 Python 继续给 C# 结果打补丁 | 不建议 | 已出现远程修甲重复扣除、同名字段不同真值、调度顺序不一致 |
| 所有引擎代码从零全部重写 | 不建议 | 丢失已验证基础公式、类型加载、快照与投射；仍无法绕过特殊效果覆盖工作 |
| **保留外壳和基准，分层替换效果核心与统一事件模拟** | **推荐** | 能逐领域对照迁移，保留正确能力，消除主要根因 |
| 直接采用 Pyfa/eos | 可另行评估 | 规则覆盖有参考价值，但需实测部署、版本/数据适配和各组件许可证；不能直接混入现有 MIT 代码就假定可以原样分发 |

推荐目标结构：

```text
版本化 SDE + 明确的特殊效果注册表
         ↓
强类型对象/属性依赖求值器
  明确作用域、状态、运算顺序、叠加组、依赖失败
         ↓
唯一的标准化模块结果
  伤害/维修每轮量、周期、弹药单位/轮、弹夹、换弹、耗电、投射距离
         ↓
唯一事件调度器 + 纯函数应用/防御计算
         ↓
带单位、来源、规则覆盖及可信状态的结果契约
         ↓
```

## 建议执行顺序与验收

1. **先冻结正确性基线。** 把本轮样本、精确技能快照、SDE/规则版本与预期公式纳入正式测试。建立错误/未知值状态。83 个审查检查中确认的缺陷应变成会阻止合并的正式回归测试；本轮探针用于报告差异，本身不会因发现已知错误而退出失败。
2. **先收敛结果契约。** 统一本地/远程维修、EHP、理论/含换弹 DPS、峰值回充；删除跨语言纠错及较大值回退。先避免用户界面和 API 给出不同答案。
3. **替换效果执行与覆盖机制。** 保留经过测试的属性算术组件，重构对象作用域、状态、特殊处理器和依赖错误传播；从本轮确认的导弹/无人机、推进、辅助维修、falloffEffectiveness 开始，逐项验收候选效果清单。
4. **合并事件模拟器。** 电容、注电、换弹、维修、失败重试、外来事件都使用同一精度和排序规则；建立每轮耗电/弹药守恒、同刻优先级、采样窗口边界测试。Python 原来的两个调度循环退休。
5. **修正靶标输入模型。** 独立记录双方速度向量、距离和半径；导出目标绝对速度与相对角速度；不要用一个 `speed` 字段兼任。
6. **扩大独立对照后再宣称正确。** 固定同版本数据，做 Pyfa/客户端金样：代表舰种、0/IV/V 技能、T1/T2、状态、脚本、弹种、数量、叠加、远程/辅助模块。不能只用当前实现自身输出生成预期。

发布验收应至少要求：本轮确认错误全部通过回归；已声明支持的效果没有静默未处理项；核心字段只有一个来源；同版本跨引擎差异有明确容差和逐项解释。暂未核准的机制应降级为“未验证/不支持”，而不是用估算回填成精确值。
