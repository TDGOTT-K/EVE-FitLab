# FitLab 第一阶段：静态配装计算闭环

状态：发布基线草案

本文档是 FitLab 第一阶段的产品定义、支持边界和发布门禁。它优先于旧的原型描述、旧引擎 beta 说明和“与 pyfa 结果接近”的判断。第一阶段使用独立 N 号引擎作为数值权威；旧引擎 beta 不属于本阶段发布基线。

## 1. 一句话定义

> 给定一个带版本的舰船配装、角色技能、物品实例、库存和静态计算上下文，FitLab 能够对该配装进行可重现、可解释、无静默降级的合法性检查和性能计算，并支持完整编辑、保存、导入、导出和分享。

这里的“完整”指阶段一明确声明支持的静态配装域完整，不要求已经具备战斗沙盒或逐 tick 战斗模拟。

第一阶段的正式名称是：**FitLab 静态配装计算闭环**。

## 2. 第一阶段的产品承诺

用户可以：

1. 选择舰船、舰体模式、角色技能和配装上下文。
2. 安装、替换、卸载和配置阶段一支持范围内的装备及实体物品。
3. 看到资源、属性、攻击、防御、机动、电容、估价和目标应用结果。
4. 理解每个结果的计算口径、输入、来源、完整性和未计入项。
5. 保存非法或不完整的配装草稿，但不会把它显示为合法或完整。
6. 通过 UI、公开 MCP 和公开 CLI 对同一输入得到相同的业务结果。
7. 在保存、导入、导出、分享和重新打开后恢复相同的规范化配装输入和 `fitHash`。

第一阶段不承诺“所有 EVE 机制已经实现”，而承诺所有未实现或不适用的内容都被明确表达，不被静默当作零值、默认值或已计算结果。

## 3. 阶段一配装对象模型

阶段一必须无损表达以下对象。每个对象都必须有稳定身份、版本来源和可序列化表示；显示名称不能作为唯一身份。

### 3.1 舰船与槽位

- 舰船类型和舰体基础属性；
- 舰体模式及模式切换后的槽位、属性和限制；
- 高槽、中槽、低槽；
- 改装件槽位；
- 战略巡洋舰 T3 子系统及子系统类型；
- 炮塔和发射器挂点；
- 槽位顺序、槽位身份和空槽；
- 装备安装位置和替换关系。

### 3.2 模块、弹药和实体物品

- 模块类型、模块实例和稳定的类型 ID / 实例 ID；
- 在线、离线、主动和超载状态；
- 弹药类型、兼容性和实际装填数量；
- 普通弹药与备弹库存；
- 晶体实体、实体 ID、累计损伤、装载位置和备用晶体；
- 深渊装备实例、原始类型、实例 ID、突变来源、变异属性和变异规则版本；
- 深渊装备的生成、导入、复制、替换、卸载和保存；
- 不允许用普通类型 ID 替代晶体、深渊实例或其他具有实体状态的物品。

### 3.3 机库与库存

- 普通无人机库存、出动数量和备用数量；
- 舰载机机库、编队/中队身份、成员数量、部署数量和备用数量；
- 舰载机静态属性、静态主武器和可选静态贡献；
- 货舱、备弹、注电、晶体和其他阶段一静态库存；
- 数量、体积、容量、超限和库存不足诊断；
- 未声明、明确为零和实际为零必须可区分。

第一阶段不要求完成舰载机补员、特殊能力、战斗时序、无人机追击或实体死亡，但不得丢失这些对象的静态身份和库存信息。

### 3.4 角色、脑插和增效剂

- 角色技能快照、技能等级、来源和快照版本；
- 无技能、全技能 V、自定义技能和 EVE SSO 导入的角色快照；
- 脑插槽、脑插物品、套装身份和脑插效果；
- 增效剂类型、服用方案、副作用选择、持续时间和随机回执；
- 增效剂与脑插对静态属性、资源、攻击、防御和其他适用结果的影响；
- 脑插和增效剂方案必须进入保存、撤销、重做、导入、导出、分享和 `fitHash`；
- 随机结果必须有种子/回执或明确不可用状态，重复分析不能无原因重新抽样。

脑插、增效剂和深渊变异不是可选增强项，而是第一阶段的正式范围。即使 pyfa 没有同等能力，也不能将它们降为第二阶段或作为“与 pyfa 对照失败”的理由。

### 3.5 装配元数据和计算上下文

- 装配名称、标签、备注和文件夹归属；
- 目标装配、目标抗性、距离、速度、角速度、信号半径等静态目标上下文；
- 攻击口径：名义 DPS、目标应用 DPS/EDPS、选定武器集合和分项选择；
- 电容起始条件、外部传电/毁电来源、库存和观察窗口；
- 估价范围、数量声明、价格来源、获取时间、缓存状态和缺报价；
- SDE 版本、规则版本、引擎版本、公开契约版本和必要内容哈希。

## 4. 第一阶段静态规则范围

对于阶段一支持矩阵内的对象，所有装配时即可决定的规则必须由 N 号引擎计算或明确返回不可用原因。

### 4.1 必须正确处理

- 槽位数量和槽位类型；
- 炮塔、发射器和改装件挂点；
- CPU、能量栅格和校准值；
- 舰船模式和模式专属限制；
- T3 子系统的舰体匹配、类型匹配和安装限制；
- 货舱、无人机舱、舰载机舱、带宽和容量；
- 角色技能前置、技能等级和技能作用域；
- 物品适用舰船、装备组、尺寸、科技等级和数量限制；
- 模块在线、离线、主动和超载合法性；
- 弹药兼容性、装填数量和库存容量；
- 晶体实体、耐久、装载/卸载/交换和备用身份；
- 深渊实例的原类型、变异属性、范围、规则版本、技能门槛和实例身份；
- 脑插槽、套装、互斥和属性影响；
- 增效剂前置、副作用、服用方案、持续时间和已确定随机结果；
- 无人机和舰载机的静态库存、数量、部署限制和静态贡献；
- 装备互斥、主动组数量和其他已由引擎公开支持的准入限制；
- 结构错误、未知物品、重复身份、版本不匹配和输入大小边界；
- 资源超限、缺失条件、部分覆盖和不支持效果。

### 4.2 静态指标至少包括

- 舰船属性和舰体模式属性；
- CPU、能量栅格、校准值、槽位和挂点；
- 护盾、装甲、结构、抗性、HP 和 EHP；
- 速度、机动、锁定、射程、跟踪、信号半径和角速度相关读数；
- 名义伤害、名义 DPS 和分项贡献；
- 弹药、晶体、脑插、增效剂、变异实例对结果的影响；
- 固定目标下的应用 DPS/EDPS；
- 炮台距离、信号半径、角速度采样和目标上下文；
- 无人机和舰载机的静态贡献；
- 电容容量、平均负载、可用性和已支持的静态传电/毁电投影；
- 主动维修及其他已接入的静态投影；
- 装配估价及报价来源、范围、缺项和时间状态。

### 4.3 明确允许延期的运行时机制

以下内容不阻止第一阶段，但其静态输入、来源和不可用原因必须保留：

- 逐 tick 舰船战斗；
- 舰船运动、碰撞和完整空间时序；
- 导弹飞行、拦截和路径生命周期；
- 无人机追击、碰撞和动态目标选择；
- 电子战完整运行时；
- 维修、换弹、热量和资源竞争的完整时间线；
- 舰船死亡、离场、重组和战斗检查点；
- 星门、跨星系实体迁移；
- 战斗脚本和战斗沙盒。

延期能力必须显示为类似“静态属性已计算，运行时行为尚未支持”，不能隐藏模块的静态 CPU、PG、槽位、属性修正或装配错误。

## 5. 指标和解释契约

任何在 UI、图片、导出文件或 API 中展示的业务指标，至少必须携带：

```json
{
  "value": 100,
  "unit": "dps",
  "state": "available",
  "complete": true,
  "metric": "nominalCycleDps",
  "context": {},
  "source": {},
  "selected": [],
  "notIncluded": [],
  "reason": null
}
```

实际字段可以按公开契约命名，但语义必须等价。

指标必须说明：

- 是名义结果还是目标应用结果；
- 是否扣目标抗性；
- 是否包含无人机和舰载机；
- 是否包含脑插、增效剂和深渊变异；
- 是否包含换弹、有限弹药和库存限制；
- 是否只统计选定武器集合；
- 是否存在未计入贡献；
- 使用的角色、目标、观察窗口、SDE、规则版本和引擎版本；
- 是否为完整、部分、不可用、近似或未支持结果。

`0`、`null`、`unsupported`、`invalid`、`partial` 不得互相转换。真实零必须保留为零；缺失值必须保留缺失原因。

## 6. 状态模型

第一阶段至少定义以下四类外部状态：

| 状态 | 含义 | 是否可保存 | 是否可称为合法装配 | 是否可显示诊断数值 |
|---|---|---:|---:|---:|
| `valid` | 输入合法、阶段一相关规则完整、结果完整 | 是 | 是 | 是 |
| `invalid` | 输入或装配规则错误，例如 CPU/PG、挂点或库存超限 | 是，作为草稿 | 否 | 可以，必须标注诊断性质 |
| `partial` | 可计算部分结果，但存在明确未计入项或不完整上下文 | 是，作为草稿 | 否，除非具体准入另有定义 | 是，必须列出缺口 |
| `unsupported` | 当前输入或机制超出阶段一支持范围 | 是，作为草稿 | 否 | 仅显示独立可用分项 |

引擎内部可以额外使用 `unknown`、`available`、`unavailable`、`state/reason` 等细粒度状态，但 UI 不能把它们折叠成一个“计算通过”。

资源超限必须按引擎明确的阻断告警进入 `invalid`，不能只检查 `errors` 数组。结构错误、不支持效果和部分输出必须分别保留。

## 7. 编辑和数据闭环

第一阶段必须完成：

- 创建、复制、重命名、删除装配；
- 安装、替换、卸载和批量装填；
- 脑插、增效剂、晶体、深渊实例、无人机、舰载机和库存编辑；
- 撤销、重做和编辑历史边界；
- 保存、并发冲突、版本冲突和重复请求幂等；
- 保存失败、引擎已保存但 UI 库失败、响应丢失后的重试和恢复；
- 原生会话和 UI 装配库的一致性；
- EFT 文本导入；
- FitLab 分享码导出/导入；
- 图片分享和图片导入；
- 保存后重新打开仍能得到相同规范化输入、来源和 `fitHash`；
- 导入/导出不丢失实例身份、库存、技能、脑插、增效剂、副作用和变异属性。

### 7.1 Canonical fit 规则

阶段一必须定义唯一的规范化装配文档。默认状态、字段省略、空库存、零数量、实体顺序和数值格式必须有明确规则。

原始输入 JSON 与规范化文档可以不同，但以下结果必须一致：

- 规范化装配文档；
- `fitHash`；
- N 引擎分析输入；
- UI、MCP 和 CLI 的分析结果。

不允许用“返回结果大致相同”代替规范化和哈希一致性。

## 8. 可重现和公开重放

相同的以下输入必须产生相同结果：

- 规范化装配快照；
- 角色技能快照；
- 物品实例和晶体状态；
- 脑插、增效剂方案及随机回执；
- 深渊变异属性、种子和规则版本；
- 目标上下文和观察窗口；
- SDE 数据和内容哈希；
- 引擎版本、规则版本和公开契约版本。

每个阶段一业务指标都必须可以通过公开 MCP 和 CLI 重放。FitLab 私有 Python 或浏览器 JavaScript 可以负责适配、布局、单位转换和格式化，但不得成为唯一业务计算入口。

## 9. 第一阶段完成标准

第一阶段只有在以下六条同时满足时才能关闭：

1. **输入完整**：支持矩阵内的舰船、装备、实例、库存、角色、脑插、增效剂、变异物和上下文均可无损表达。
2. **规则完整**：支持矩阵内的静态装配规则没有静默遗漏；运行时未实现项有明确原因。
3. **指标完整**：公开指标均有口径、来源、上下文、完整性、未计入项和不可用原因。
4. **状态诚实**：合法、非法、部分、不支持、未知和真实零不混淆。
5. **数据可复现**：保存、导入、导出、分享和重新打开保持规范化输入、来源和 `fitHash`。
6. **接口可重放**：UI 中的业务数值能由公开 MCP/CLI 以同输入复算，且结果、来源和排除项一致。

“与 pyfa 结果相同”不是完成条件。pyfa 只作为交互参考、常见装配的外部交叉校验和差异发现工具；FitLab 的正式规范是 N 引擎、版本化数据、状态语义、来源链和公开重放契约。

## 10. 发布门禁

### G0：范围和版本冻结

- [ ] 发布版本不再使用旧引擎 beta 的版本号和说明；
- [ ] 新引擎版本、契约 revision、SDE build、规则版本和来源哈希已冻结；
- [ ] `phase1-support-matrix` 已提交，所有对象和规则都有明确的支持状态；
- [ ] 第一阶段之外的战斗功能不会出现在“已支持”宣传文案中；
- [ ] 旧版本被标记为 legacy，不覆盖旧 Release 资产。

### G1：数据模型和规范化

- [ ] 所有阶段一对象都有稳定类型/实例身份；
- [ ] 晶体、弹药、脑插、增效剂、深渊实例和库存不丢实体状态；
- [ ] canonical fit 文档已冻结；
- [ ] 默认状态、空字段、零值、顺序和数值格式有测试；
- [ ] 同一规范化输入得到同一 `fitHash`；
- [ ] 非法输入不会写入半完成或污染的记录。

### G2：规则和状态

- [ ] 每个支持矩阵条目至少有一个正常样例和一个边界/拒绝样例；
- [ ] CPU、PG、校准、挂点、子系统、库存、晶体、变异、脑插和增效剂均有回归样例；
- [ ] 在线、离线、主动、超载状态分别有样例；
- [ ] 资源超限 warning 能正确进入 `invalid`；
- [ ] 不支持效果不会把相关结果填成 0；
- [ ] `valid / invalid / partial / unsupported` 的 UI、API、图片和导出语义一致；
- [ ] 真实零、缺失、部分和不支持有独立断言。

### G3：指标和解释

- [ ] 舰船、资源、攻击、防御、机动、锁定、电容、估价和目标应用指标都有口径；
- [ ] DPS/EDPS 明确目标抗性、武器选择、无人机/舰载机、弹药和观察窗口；
- [ ] 脑插、增效剂和深渊变异对结果的影响可追溯；
- [ ] 每个公开指标都携带来源、上下文、完整性和未计入项；
- [ ] 估价标明报价来源、时间、缓存状态、缺报价和数量范围；
- [ ] UI 不含只能在前端得到的业务公式。

### G4：编辑和持久化

- [ ] 创建、复制、改名、删除、安装、替换、卸载、批量装填通过；
- [ ] 撤销/重做覆盖模块、弹量、晶体、库存、技能、脑插、增效剂、变异实例和元数据；
- [ ] 保存期间切换装配不会串写 ID、revision 或回执；
- [ ] 并发冲突和旧 revision 被拒绝；
- [ ] 丢响应重试不会重复创建或重复应用命令；
- [ ] 原生会话导出与 UI 库保存快照一致；
- [ ] 失败恢复不破坏旧的已保存版本。

### G5：导入、导出和分享

- [ ] EFT 导入能保留可表达的阶段一信息，并对无法表达的字段给出损失清单；
- [ ] FitLab 分享码往返保持 canonical fit 和 `fitHash`；
- [ ] 图片分享包含版本、来源、状态和装配码；
- [ ] 图片导入后能恢复相同输入，不覆盖已有装配；
- [ ] 晶体、增效剂、脑插、深渊实例、技能快照和库存往返不丢失；
- [ ] 截断、重复、乱序、损坏和未知字段有明确错误或部分状态。

### G6：UI / MCP / CLI 一致性

- [ ] 每个业务面板至少有一条 UI → API → N 引擎 → MCP/CLI 对照；
- [ ] 数值、单位、来源、选定集合、排除项、状态和原因一致；
- [ ] 预览结果等于提交结果；
- [ ] 撤销/重做结果可由公开接口重放；
- [ ] 脑插、增效剂和变异实例至少各有正常、边界和不支持样例；
- [ ] 相同输入重复分析不改变随机回执或结果。

### G7：构建和安装

- [ ] 使用锁定的 N 引擎源码和固定 SDK 构建成功；
- [ ] N 引擎、SDE、规则和公开契约来源清单随包保存；
- [ ] 包内只使用打包的后端、CLI、数据和运行时；

## 11. 推荐的最小验证样例集

第一阶段至少准备以下可重复 fixture，每个 fixture 都要保存输入、期望状态、关键指标和 MCP/CLI 对照结果：

1. 无技能普通舰船空装配；
2. 全技能 V 普通炮台、弹药和固定目标；
3. 在线、离线、主动、超载四种模块状态；
4. CPU/PG/挂点/校准超限；
5. T3 舰体和四类子系统匹配/不匹配；
6. 普通无人机、舰载机静态库存、部署和备用数量；
7. 普通货舱、备弹、明确零数量和未声明数量；
8. 晶体实体、损伤、备用、交换、卸载和撤销；
9. 脑插单件、套装、互斥和技能影响；
10. 增效剂正常方案、副作用方案、随机回执和重放；
11. 深渊装备生成、导入、变异范围、实例复制和保存；
12. 缺技能、未覆盖静态效果和运行时不支持效果；
13. 目标距离、速度、角速度、抗性和 EDPS；
14. 外部传电/毁电、有限库存和不可用原因；
15. 估价有报价、零报价、缺报价、缓存和过期状态；
16. EFT、分享码、图片分享和图片导入往返；
17. 保存冲突、丢响应、重试、切换装配和失败恢复。

## 12. 发布结论

只有 G0 至 G8 全部通过，且推荐 fixture 集的 UI/MCP/CLI 对照全部通过，才能宣布第一阶段完成。

在此之前可以发布内部 preview，但发布名称必须明确是 **N 号引擎静态配装预览版**，不能称为第一阶段完成版，也不能把旧 `0.1.2-beta.1` 的计算结果或 Release 资产当作新产品发布。
